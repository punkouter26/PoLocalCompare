Architecture dashboard · three depths

A duel where only one fighter is on the payroll

PoLocalCompare puts two language models on the same prompt and watches them race to write HTML. The thing that makes it awkward to document — and interesting to build — is that the two sides do not run in the same place. One side executes in an Azure datacenter and bills per token. The other executes on the viewer's GPU, inside the browser tab, and costs nothing but watts. The server orchestrates a race it can only half see.

Chapter one

The asymmetric wager

Cloud models cost money per token. Browser models cost only electricity. The app exists to answer, with measured evidence instead of vibes, whether a free local model is actually competitive with a paid cloud one for practical HTML-generation work — in speed, in output quality, and in cost.

Chapter two

Catalog & cost

Twenty-one models ship in the seed catalog. Just over half are Foundry deployments that bill per token; a third run in the browser for free; two are Ollama models that only exist on a developer's own machine. Only five of the twelve remote deployments carry a verified price — the rest are deliberately left blank, because a guessed rate becomes a wrong number on the leaderboard's cost column.

Pricing is null on purpose for GPT-5.4, GPT-5 Mini, GPT-4.1 Mini, Llama 3.3 70B, Codestral 2501, Kimi K2.7 Code and Grok 4.1 Fast. Implementation

The catalog is spread across three files that must agree, and the seeder only runs when the Models table is completely empty — editing it changes nothing on a machine that has already run. Wipe Azurite (docker compose down -v) or the new entry never appears.

Chapter three

One duel, end to end

A person picks two models and a prompt on the home page and presses Compare. The steps that follow are a real sequence, so they are numbered:

  1. Commence. The click POSTs the pairing and prompt. The server writes a duel row and immediately navigates the browser to the Arena — there is no waiting-room page.
  2. Queue. Execution is handed to a background worker, so the HTTP request returns in milliseconds while the duel runs on.
  3. Race. Both sides start at once. Server-side models stream tokens the server counts; a browser-side model is told to start over SignalR and runs on the viewer's GPU.
  4. Watch. The Arena shows both outputs building live, in sandboxed preview frames, with token velocity and a warm-up reading per side.
  5. Converge. Both results land in storage, the Arena is told the duel is complete, and the verdict UI replaces the race.
  6. Decide. A human pick wins if it arrives inside the grace window. Otherwise an AI judge reads both outputs and records the verdict itself.

Systems

The payload lifecycle

A mixed duel — one Foundry model, one browser model — which is the case that exercises every path at once.

The judge runs inline rather than as a second queued item. The background service awaits each work item before dequeuing the next, so a queued delay would stall the following duel — and a duel isn't finished until it has a verdict, which makes blocking there the honest shape.

Two rendering details keep the Arena from tearing itself apart while tokens arrive faster than a frame:

  • RenderCoalescer.Request() batches per-token updates on a ~16 ms trailing edge. Terminal events (DuelComplete, verdicts) bypass it and paint immediately.
  • SandboxedViewport implements ShouldRender gated on an ordinal compare of its raw HTML — without it every render re-emitted srcdoc and the browser tore down and reloaded the preview mid-generation.

Chapter four

Verdicts, ELO, and three invariants

A duel is not over when the models stop typing — it is over when somebody decides who won. A person who picks a winner in the Arena inside the grace window always decides it. Otherwise an AI judge is asked which output followed the prompt better, and it records the verdict itself. Either way the rating only ever moves once.

Systems

How a duel reaches a verdict

Every terminal state except Pending has moved ELO exactly once.

The three invariants

  • A human decision always wins the race. AutoJudge re-reads the duel after its delay and stands down on anything but Pending; RecordVerdictHandler throws on a second verdict.
  • No evidence, no movement. An unreachable judge, an unparseable reply, or two failed models all leave the duel Pending. ELO never moves on a guess.
  • The switch genuinely reverts. AiJudge:Enabled=false restores the original human-only behaviour; the demo runner's delay override is clamped 0–3600 and cannot switch the judge on.

The default 5-second window this feature shipped with was too short to read two outputs, so the judge decided nearly every duel. It is 60 s now — widen it further if the human path needs to be genuinely usable, because a window nobody can act inside is a human-in-the-loop in name only.

Implementation

Every verdict carries its source. Never add a write path that moves ELO without setting it — the leaderboard would blend two different signals with no way to separate them afterwards.

Chapter five

Who may call what

Authorization is deny-by-default: the fallback policy requires an authenticated user, so a new endpoint is closed until somebody opens it on purpose. Twenty-six surfaces are mapped in Production. Fifteen require a session, two open only when a feature flag says so, and nine are anonymous — five of which are the sign-in and liveness surfaces that have to be.

There are no roles. A role claim is carried through the whole system and no endpoint reads it; adding role-based gating would mean introducing named policies that do not exist today.

Three mechanics decide every cell above:

  • The fallback policy. FallbackPolicy = RequireAuthenticatedUser in Program.cs — anything not otherwise annotated is closed.
  • Registration order. Calling AllowAnonymous() on a group that already called RequireAuthorization() loses. DuelsEndpoints works around this by capturing the RouteHandlerBuilder and applying the override afterwards.
  • The fake scheme cannot exist in Production. FakeAuthHandler's constructor throws InvalidOperationException when the host environment is Production, so even a misconfigured registration cannot grant access there.

Chapter six

What is persisted

Four Table Storage tables hold everything: the duels, the two result rows per duel, the model registry, and the rating history. There is no relational database and no ORM — partition and row keys are the whole index, so how a row is keyed decides what queries are cheap.

Systems

Entities and their relationships

Four tables; LeaderboardEntryDto is projected on read, never stored.

Implementation

Three persistence behaviours bite if you forget them:

  • Writes are idempotent and ETag-safe. Creates swallow 409; updates are If-Match conditional; duel writers re-read and reapply on 412.
  • HybridCache fronts the hot reads. 30 s TTL, tag-invalidated on verdict, over the leaderboard and model-availability queries. A new write path that affects either must invalidate it.
  • Typed HttpClients use retry-only resilience. Adding a per-attempt timeout would abort the SSE streams the Arena depends on.

    public static DuelId From(string value) => new(value);

Chapter seven

How it is proven

Four test projects, one per tier, held to a fixed proportion rather than allowed to pile up wherever tests are easiest to write. Three of the four gate the deploy. The fourth — the browser suite — deliberately does not, and is therefore the one that goes stale silently.

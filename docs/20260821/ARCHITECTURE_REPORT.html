Architecture Report · PoLocalCompare

Single-host topology, three inference paths, asymmetric execution

Sources: Program.cs, GlobalUsings.cs, Features/*/Endpoints.cs, App.razor, Common/Background/*. Generated 2026-08-21. C4 Container (level 2) + Component (level 3) views in order: Executive → Architectural → Implementation.

TIER 1Executive summary (30 s)

One host, two assemblies (Client = Blazor WASM, Api = minimal APIs). The Blazor client is served from the API at https://localhost:5001 — single origin, no CORS. Inference runs through three paths (Remote, LocalService, Local/WebLLM) but state, persistence, and the global activity ticker always converge in Azure Table Storage and SignalR. Authentication is BFF (encrypted HttpOnly cookie); the WASM tab never sees a token. State is stored as five strongly-typed records (Duel, DuelResult, Model, EloRecord, LeaderboardEntryDto).

Things you must NOT lose when editing this architecture

  • Single write path for ELO. RecordVerdictHandler throws on a second verdict and refuses a verdict with both sides failing (GuardAgainstNoEvidenceAsync). Bypass this and the leaderboard silently blends two signals.
  • Browser-side logic lives in PoLocalCompare.Shared. Only the API is reachable from unit tests; pure helpers in Client/ are invisible to all CI tiers.
  • WebLLM worker needs a cache-buster. new Worker('/js/webllm-worker.js?v=N') — bump N or changes appear to do nothing. Same trap on theme.js, util.js, diag-interop.js, compare.js.
  • Cache invalidation is explicit. HybridCache tag CacheTags.Leaderboard is invalidated by RecordVerdictHandler after every verdict write.
  • One host, no CORS. Adding a CORS policy accidentally crosses session cookies in unintended ways. The Blazor client is served from wwwroot/ by this API; cross-origin isn't a thing.
  • Typed HttpClients use retry-only pipelines. Foundry/Ollama proxies get retry only — a per-attempt timeout would abort long SSE streams.

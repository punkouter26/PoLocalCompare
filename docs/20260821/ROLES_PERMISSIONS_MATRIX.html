TIER 1Executive summary (30 s)

There are three effective principals in this codebase: Anonymous (no cookie, no fake header), Authenticated (BFF cookie or X-Fake-User in non-Production), and Fake (header-supplied identity, Development only). The role claim is carried but no endpoint reads it — there are no role-based policies. The single authorization policy is RequireAuthenticatedUser attached to every group via RequireAuthorization(); endpoints opt out explicitly with .AllowAnonymous().

No role-based authorization (claims carried, never read) Deny-by-default fallback 3 effective principals 2 environments (Development / Production) 4 non-auth endpoints AllowAnonymous() in every environment

The single effective policy

// src/PoLocalCompare.Api/Auth/BffAuthentication.cs
var schemes = isProduction
    ? new[] { CookieAuthenticationDefaults.AuthenticationScheme }
    : [CookieAuthenticationDefaults.AuthenticationScheme, FakeScheme];

options.DefaultPolicy = new AuthorizationPolicyBuilder(schemes)
    .RequireAuthenticatedUser()
    .Build();
options.FallbackPolicy = options.DefaultPolicy;          // deny-by-default

// Cookie events turn redirect-style challenges into plain JSON status codes:
options.Events.OnRedirectToLogin       = ctx => { ctx.Response.StatusCode = 401; return Task.CompletedTask; };
options.Events.OnRedirectToAccessDenied = ctx => { ctx.Response.StatusCode = 403; return Task.CompletedTask; };

This means no endpoint can be reached by Anonymous except those that explicitly opt out. The opt-outs are listed in the matrix below. The cookie event handlers guarantee an unauthenticated API call gets a JSON 401, never a 302 to an HTML login page — the BFF login route is the only interactive surface.

Security audit flags

  • Always-anonymous endpoints (4): /api/duels/{id}/local-result, /api/models/download-status/{webLlmId}, /health, /api/diag/smoke. Each is intentionally so — the WebLLM worker has no cookie, the download-status probe is filesystem-only, and the diagnostics are needed for liveness probes.
  • Dev-only endpoints (5): /auth/login/fake, /scalar, /openapi, /api/dev/reset, /api/dev/remap-model-ids. All wrapped in app.IsDevelopment() and therefore not mapped in Production at all.
  • Conditional writes (2): POST /api/duels and POST /api/duels/{id}/verdict are gated by the Features:AllowAnonymousWrites flag (default false). Reads always require auth, so the leaderboard & archive can't be scraped anonymously.
  • No fine-grained roles. The ClaimTypes.Role claim is emitted by both /auth/login/fake and the Fake header scheme, but no IAuthorizationHandler reads it. Adding role-based gating would require extending Program.cs with named policies (builder.Services.AddAuthorization(o => o.AddPolicy("Admin", …))) and decorating endpoints with .RequireAuthorization("Admin").
  • Defense in depth on FakeAuthHandler. Constructor throws InvalidOperationException if constructed in a Production IWebHostEnvironment — so even a misconfigured AuthenticationSchemeOptions registration of Fake cannot grant access in Production.
  • IdentityResolver (used by DuelsEndpoints). Always stamps the actor on write paths even when the cookie is anonymous (it returns the literal string "anonymous" in that case), so audit trails remain consistent regardless of auth state.

How to read a Cond. cell

Cells marked Cond. depend on a runtime config flag (Features:AllowAnonymousWrites) and on whether the request carries a session cookie. The matrix shows the worst case (Dev / flag on, no cookie). Flip the flag or restart the app to change it.
